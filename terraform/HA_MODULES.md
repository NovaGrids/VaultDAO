# VaultDAO Terraform — HA Backend Modules

This document covers the new reusable Terraform modules added to support
high-availability staging and production deployments of the VaultDAO backend
(API, Postgres, Redis, secrets management, and CI/CD).

---

## Directory layout

```
terraform/
├── modules/
│   ├── networking/        # VPC, subnets, NAT, security groups
│   ├── postgres/          # RDS PostgreSQL + Secrets Manager
│   ├── redis/             # ElastiCache Redis + Secrets Manager
│   ├── secrets/           # App secrets + IAM read policy
│   ├── container_service/ # ECS Fargate + ALB + ECR + auto scaling
│   └── ci_oidc/           # GitHub Actions OIDC IAM role
└── environments/
    ├── staging/           # Staging root module (cost-optimised)
    └── production/        # Production root module (HA, deletion protection)
```

The `modules/` tree also contains the existing `vpc/`, `backend/`, `database/`,
`redis/`, `rpc_pool/`, and `monitoring/` modules from the original EKS-based
configuration. The new modules are designed for a simpler ECS Fargate topology
that matches the `docker-compose.yml` intent without requiring Kubernetes.

## Modules

### `networking`

Creates a three-tier VPC:

- **Public tier** — ALB only. No ECS tasks or databases here.
- **Private tier** — ECS Fargate tasks with outbound-only NAT access.
- **Data tier** — RDS Postgres and ElastiCache Redis. No internet route.

Security groups use `source_security_group_id` references (not CIDR blocks)
so the trust relationship between tiers survives VPC CIDR changes.

**Threat notes — exposed ports:**

| Port | Service | Allowed source | Threat if misconfigured |
|------|---------|---------------|------------------------|
| 443/80 | ALB | `0.0.0.0/0` | Intended public access; ALB forwards only to app tier |
| `app_port` | ECS | ALB SG only | Direct container access from internet blocked by SG |
| **6379** | **Redis** | **App SG only** | **Redis has no auth by default; exposure = full data access** |
| **5432** | **Postgres** | **App SG only** | **Postgres exposure = credential bypass risk** |

Redis and Postgres ports are opened **only to the app security group** (`app_sg_id`).
No CIDR block rule exists for these ports. The `SecurityNote` tag on the Redis
SG makes the intent explicit for auditors.

### `postgres`

RDS PostgreSQL with:

- Storage encryption (AWS-managed or CMK)
- Multi-AZ standby (configurable, default `true`)
- Password generated by Terraform and stored in **Secrets Manager** — never in
  `.tfstate` in plaintext (it is sensitive but still state-resident; use a
  remote, encrypted backend)
- `publicly_accessible = false` — second defence layer after the SG
- `rds.force_ssl = 1` parameter group — TLS required on all connections
- Performance Insights (production only) + CloudWatch log export

**Threat notes — secrets:**

The database password is in Terraform state. Use an S3 backend with:
- Server-side encryption (`encrypt = true`)
- S3 bucket policy denying non-TLS access
- DynamoDB state locking

Never output `connection_string` to CI logs. Use `secret_arn` to inject
credentials into ECS tasks instead.

---

### `redis`

ElastiCache Redis replication group with:

- **Transit encryption enabled** (`transit_encryption_enabled = true`) — TLS required
- **At-rest encryption** (`at_rest_encryption_enabled = true`)
- **AUTH token** — randomly generated 64-character token stored in Secrets Manager
- Data-tier subnet group only — no public subnets
- Security group from `networking` module (6379 from app only)
- Slow-query and engine-event logs to CloudWatch

**Threat notes — no public Redis:**

The `docker-compose.yml` binds Redis to `redis:6379` on a private bridge
network. This module preserves that intent: Redis sits in the data-tier subnet
with no route to the internet and no security group rule allowing inbound from
any CIDR. The only inbound rule is `source_security_group_id = app_sg_id`.

AUTH tokens are stored in Secrets Manager under
`vaultdao/<env>/redis/auth-token` and injected into ECS tasks via
Secrets Manager injection (no plaintext in task definition).

---

### `secrets`

Centralises application secrets in Secrets Manager:

- JWT signing secret (auto-generated, 64 chars)
- Application config bundle (Stellar contract ID, RPC URL, CORS origin, etc.)
- IAM policy granting `secretsmanager:GetSecretValue` only on specific secret
  ARNs for the environment — no wildcard

**Threat notes — secret management:**

- Secrets use `recovery_window_in_days = 30` in production to prevent
  accidental permanent deletion.
- The read policy lists exact ARNs, not `arn:aws:secretsmanager:*:*:secret:vaultdao/*`.
  This prevents cross-environment secret reads if IAM principals are shared.
- Rotate secrets by running `terraform apply` after removing the
  `ignore_changes` lifecycle or via Secrets Manager automatic rotation (not
  configured in this module; add `aws_secretsmanager_secret_rotation` for
  production hardening).

### `container_service`

ECS Fargate service with:

- Application Load Balancer (HTTPS termination via ACM)
- HTTP → HTTPS redirect
- ECS task execution role (pull ECR images, read Secrets Manager secrets)
- ECS task role (CloudWatch metrics, Secrets Manager read)
- Secrets injected at task start from Secrets Manager — **no plaintext env
  vars in the task definition**
- CPU and memory auto scaling (target-tracking, 70% CPU / 75% memory)
- Deployment circuit breaker with auto-rollback
- ECR repository with `IMMUTABLE` tags and scan-on-push
- Staging uses FARGATE_SPOT to reduce cost; production uses dedicated FARGATE

**Threat notes — container security:**

- Container image must be pushed with an immutable tag in production (not
  `:latest`). ECR image tag mutability is set to `IMMUTABLE`.
- The task container runs as `user: node` (non-root).
- Secrets are **never** passed as environment variable literals in the task
  definition JSON — they are referenced by Secrets Manager ARN and resolved
  by the ECS agent at task start.
- The ALB uses `ELBSecurityPolicy-TLS13-1-2-2021-06` (TLS 1.3 preferred,
  TLS 1.2 minimum).

---

### `ci_oidc`

Keyless GitHub Actions deployments via OIDC:

- No long-lived AWS access keys stored in GitHub Secrets
- Trust policy restricted to a specific `org/repo` and either:
  - Branch claims (`allowed_branches`) — for staging
  - GitHub Environment claims — for production (requires a GitHub Environment
    named `"production"` with required reviewers)
- Deploy policy covers only ECR push and ECS service update — no IAM, no S3,
  no Secrets Manager write access

**Threat notes — CI trust boundary:**

- Production uses environment-scoped claims (`repo:<org>/<repo>:environment:production`).
  This means the CI role can only be assumed when a GitHub Actions workflow
  runs in the `production` GitHub Environment, which requires human approval.
- Do not add `"repo:<org>/<repo>:*"` as a subject claim — that allows any
  workflow in the repo (including PRs from forks) to assume the role.
- The `PassRole` permission is scoped to `ecs-tasks.amazonaws.com` and the
  exact task role ARNs of this environment.

## Quick start

### Prerequisites

- Terraform >= 1.5
- AWS CLI configured (`aws configure` or IAM role)
- S3 bucket `vaultdao-terraform-state` with versioning and encryption
- DynamoDB table `vaultdao-terraform-lock` for state locking
- ACM certificate for your domain in `us-east-1`

### Deploy staging

```bash
cd terraform/environments/staging

cp terraform.tfvars.example terraform.tfvars
# Edit terraform.tfvars with real values

terraform init
terraform validate
terraform plan -out=tfplan
terraform apply tfplan
```

### Deploy production

```bash
cd terraform/environments/production

cp terraform.tfvars.example terraform.tfvars
# Edit terraform.tfvars with real values (use immutable image tag)

terraform init
terraform validate
terraform plan -out=tfplan
terraform apply tfplan
```

### GitHub Actions workflow snippet

After deploying, add to `.github/workflows/deploy.yml`:

```yaml
- uses: aws-actions/configure-aws-credentials@v4
  with:
    role-to-assume: ${{ secrets.AWS_DEPLOY_ROLE_ARN }}  # from ci_role_arn output
    aws-region: us-east-1

- uses: aws-actions/amazon-ecr-login@v2

- name: Build and push
  run: |
    docker build -t $ECR_REGISTRY/vaultdao/backend:${{ github.sha }} ./backend
    docker push $ECR_REGISTRY/vaultdao/backend:${{ github.sha }}

- uses: aws-actions/amazon-ecs-deploy-task-definition@v1
  with:
    task-definition: task-definition.json
    service: ${{ env.ECS_SERVICE }}
    cluster: ${{ env.ECS_CLUSTER }}
    wait-for-service-stability: true
```

## State backend bootstrap

Run once per AWS account before `terraform init`:

```bash
aws s3api create-bucket \
  --bucket vaultdao-terraform-state \
  --region us-east-1

aws s3api put-bucket-versioning \
  --bucket vaultdao-terraform-state \
  --versioning-configuration Status=Enabled

aws s3api put-bucket-encryption \
  --bucket vaultdao-terraform-state \
  --server-side-encryption-configuration \
  '{"Rules":[{"ApplyServerSideEncryptionByDefault":{"SSEAlgorithm":"aws:kms"}}]}'

aws dynamodb create-table \
  --table-name vaultdao-terraform-lock \
  --attribute-definitions AttributeName=LockID,AttributeType=S \
  --key-schema AttributeName=LockID,KeyType=HASH \
  --billing-mode PAY_PER_REQUEST
```

## Security checklist

- [ ] Remote state backend uses encryption and versioning
- [ ] `terraform.tfvars` is in `.gitignore` (never committed)
- [ ] Redis `transit_encryption_enabled = true` and `auth_token` set
- [ ] Postgres `publicly_accessible = false` and `rds.force_ssl = 1`
- [ ] No security group rule opens 6379 or 5432 to `0.0.0.0/0`
- [ ] CI OIDC role uses environment-scoped claims in production
- [ ] Container image uses an immutable tag in production
- [ ] ALB uses TLS 1.3 policy (`ELBSecurityPolicy-TLS13-1-2-2021-06`)
- [ ] VPC Flow Logs enabled
- [ ] ECR scan-on-push enabled
- [ ] Deletion protection enabled on Postgres in production
